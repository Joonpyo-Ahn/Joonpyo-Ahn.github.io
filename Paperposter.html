Introduction

A common rule of thumb in data analysis is that nearly 80% of the work is spent cleaning and preparing data. Despite how much time this takes, there has been relatively little focus on how datasets should be structured for effective analysis.

This presentation focuses on data tidying , a key part of data cleaning. The main idea of tidy data is to organize datasets so their structure clearly matches their meaning. By reducing repetitive data manipulation, tidy data helps analysts spend more time on meaningful questions instead of technical cleanup.

Defining Tidy Data

“Happy families are all alike; every unhappy family is unhappy in its own way.” — Leo Tolstoy

Like families, tidy datasets are all alike, but every messy dataset is messy in its own way. In a structured dataset, values are organized into variables (attributes measured across units) and observations (all attributes measured on a single unit).

To be considered Tidy Data, a dataset must satisfy three strict geometric rules:

  • Rule 1: Each variable must form a single column.
  • Rule 2: Each observation must form a single row.
  • Rule 3: Each type of observational unit must form its own table.

Any other structural arrangement of data values is defined as messy data.

Tidying Messy Datasets

Real-world datasets frequently violate the precepts of tidy data. Most messy structures can be completely resolved using a small set of foundational tools, primarily melting (stacking wide columns into rows) and string splitting.

3.1 Column Headers are Values, Not Variable Names

  • This problem frequently occurs in tabular datasets designed for presentation, where variables form both rows and columns.
  • Example: The Pew Research Center survey on income and religion, where different income ranges (e.g., <$10k, $10-20k) serve as column headers instead of variable names.
  • Solution: We parameterize the dataset by its true variable column (religion) and melt (stack) the remaining columns into two new variables: income and frequency.

3.2 Multiple Variables are Stored in One Column

  • After melting a wide dataset, the resulting column headers often become a compound combination of multiple underlying variable names.
  • Example: The World Health Organization (WHO) Tuberculosis (TB) dataset contains columns like m014 and f1524, which mix both sex (m/f) and age demographic groups (0-14/15-24) together.
  • Solution: Tying this data requires a string splitting operation or lookup table to separate the compound values into two distinct, semantic columns: sex and age.

3.3 Variables are Stored in Both Rows and Columns

  • This represents the most complex form of messy data, where structural components are scattered in both directions.
  • Example: Global Historical Climatology Network weather data (Station MX17004), where individual days are spread across columns (d1–d31), while actual variables like minimum (tmin) and maximum (tmax) temperatures are stored vertically as row elements.
  • Solution: We first melt the wide day columns into a uniform date variable, and then apply a cast (unstack) operation to rotate the weather elements (tmin, tmax) back out into their own independent column headers.

3.4 Multiple Types of Observational Units in One Table

A dataset can also be messy when it stores different kinds of observational units in the same table. In this case, the issue is not only the shape of the data, but also the meaning of each row.

In the Billboard example, one table contains two different units:

  • Song-level information: artist, track, and time
  • Week-level information: date and chart rank This creates repeated information because the same song details appear again for every week the song is on the chart. The tidy solution is to split the data into separate tables:
  • A song table for artist, track, and time
  • A ranking table for date and weekly rank
  • A shared id column to connect the two tables This process is related to database normalization. Each fact should be stored in one place, so the data is easier to update, join, and check for errors.

3.5 One Type in Multiple Tables

The opposite problem can also happen: one type of observational unit may be spread across many different files or tables. For example, baby name data might be stored as separate files by year 1990.csv, 1991.csv, 1992.csv

Even though the files are separate, they all describe the same kind of unit: baby names recorded by year.

If the structure of each file is consistent, the solution is straightforward:

    1. Read all files into R
    1. Add a new column that records the source file or year
    1. Combine the files into one table

4. Tidy Tools

Tidying data matters because it makes the next steps of analysis easier. Once a dataset is tidy, different tools can work together without the analyst constantly reshaping the data.

In a tidy dataset, each variable has its own column. This makes it simple for R functions to know what each part of the data means. For example, if rank, artist, and week are all separate columns, we can filter songs, group by artist, calculate summaries, and make graphs using the same structure. Tidy tools are useful because they follow the same logic:

  • They take a tidy dataset as input
  • They perform one clear task
  • They return a result that can be used in the next step
## # A tibble: 2 × 4
##   song   artist   best_rank weeks_in_top_20
##   <chr>  <chr>        <dbl>           <int>
## 1 Song A Artist 1         8               2
## 2 Song B Artist 2        12               1

This code works smoothly because the data is already tidy:

  • filter() keeps only rows where the song ranked in the top 20
  • group_by() organizes the data by song and artist
  • summarise() creates a smaller summary table

The output is still a clean table that can be used for a graph or model

This is the main value of tidy tools. They allow analysis to move step by step from cleaning, to manipulation, to visualization, to modeling.

5. Case Study: Mortality in Mexico

Wickham applies tidy data to mortality data from Mexico in 2008. The goal is to find causes of death with unusual patterns across different hours of the day.

The tidy workflow follows these steps:

    1. Count deaths by hour and cause
    1. Remove missing hour values
    1. Join disease labels to the cause-of-death codes
    1. Calculate the proportion of deaths in each hour
    1. Compare each disease pattern to the overall hourly death pattern
    1. Identify causes of death that look unusual

The case study finds that some causes of death have clear hourly patterns:

  • Murder is more common at night
  • Drowning is more common in the afternoon
  • Transportation-related deaths are more common around commute times

Conclusion

Tidy data follows three main rules: each variable is a column, each observation is a row, and each type of observational unit has its own table. This structure makes data analysis clearer and more efficient.

By reducing unnecessary cleaning work, tidy data allows analysts to focus more on the research question. It also supports a smoother workflow across cleaning, visualization, and modeling.

Although tidy data is not ideal for every complex data format, it provides a practical and reproducible standard for most tabular datasets used in R.

Why It Matters Today

When Wickham published Tidy Data in 2014, many analysts still had to create their own rules for organizing messy datasets. This paper shaped modern data formatting by providing an explicit, standardized framework for how data should be structured: variables in columns, observations in rows, and observational units in tables.

Today, that logic shapes the tidyverse, including tools like dplyr, tidyr, ggplot2, and purrr. Every time we use filter(), mutate(), or ggplot() in this course, we are using tools built on the philosophy of this paper.
